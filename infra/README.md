# Azure infrastructure (design scaffold)

This is a Bicep scaffold for a low-cost SIT demo, not a deploy-ready or security-validated release. Nothing here deploys automatically. `environments/prd.bicepparam` is a separate, intentionally unapproved placeholder; it uses demo settings and is not a production design. Use separate resource groups, credentials and state for SIT and PRD. Do not deploy PRD until its reliability, isolation, recovery and cost requirements are designed.

## Intended resources

SIT defaults to Australia East (Static Web Apps control-plane location defaults to East Asia; verify availability and residency): workload profiles v2 ACA environment with Consumption, one backend and runtime replica, Static Web Apps Free, Application Gateway Basic preview, PostgreSQL Flexible Server 16 Burstable B1ms (32 GB, no HA), classic Azure Files SMB Standard LRS, ACR Basic, Key Vault Standard, Log Analytics/Application Insights, and an S0 Azure OpenAI account. The model deployment is intentionally not created until a model/version, SKU, quota and residency are selected. No dynamic sessions or A2A applications are provisioned yet.

## Exposure and trust boundaries

- Gateway: the public IP resource exists even when the gateway is disabled; once enabled, gateway ingress is public HTTPS; Basic has no WAF. Static Web Apps Free has a public default hostname. The gateway is intended to route static paths to it and API paths to the private ACA environment.
- ACA environment and Postgres: VNet internal; the backend is reachable from the VNet and the runtime is environment-only. This is network isolation, not user authorization.
- ACR Basic, Key Vault, Foundry, Log Analytics and Azure Files: public service endpoints are enabled in this cost-conscious scaffold. RBAC, TLS and service authentication still apply. The storage account allows shared keys because the ACA Azure Files mount uses an account key. Key Vault is RBAC-protected; provision secrets using a suitably authorized operator. No firewall or private endpoints are configured for these public services. Limit access or use private endpoints in a later security design; Basic ACR lacks Private Link.
- Gateway Basic does not authenticate users. **Entra login, tenant/user allowlisting, per-route authorization and cookie/redirect handling are not implemented.** `deployUnprotectedDemo` defaults to false, so the public gateway and the runtime/backend apps are not created by default. Do not enable it until those controls are implemented and verified; changing this flag alone exposes an unauthenticated application.
- The gateway PFX is supplied as a secure parameter. Choose and operate certificate issuance/rotation; never commit PFX, passwords, or tokens. Do not place application secrets in parameter files or outputs.

## Bootstrap and validation before deployment

1. Register the Application Gateway Basic preview and confirm regional quota and feature availability. The Bicep structure compiles but gateway Basic support for disabling response buffering is unverified. Prove SSE with the actual gateway and ACA ingress, including heartbeats, reconnection and replay. If it fails, redesign the entry path before proceeding.
2. Build and push backend/runtime images to the created ACR using immutable tags. Supply fully qualified ACR image references. ACR and Key Vault must exist before the app resources can start; create the foundation with `deployUnprotectedDemo=false` first.
3. Provision `progena-database-url`, `progena-provider-encryption-key`, and `foundry-api-key` as Key Vault secrets, using private Postgres FQDN and `sslmode=require`. The current scaffold uses a single database administrator credential; replace it with least-privilege application identities/roles and explicit migrations before use. PostgreSQL `vector` is allowlisted but must also be created in the appropriate database. Verify bootstrap and checkpoint schema permissions.
4. The parameter files read `PROGENA_PG_ADMIN_PASSWORD` from the environment. The gateway certificate, hostname, and image parameters default to empty for foundation-only validation; pass them securely when application deployment is intentionally enabled. The parameter files deliberately do not contain credentials or sample image references.
5. Build and publish the Vite frontend to Static Web Apps with SPA fallback. Configure public domain, DNS, certificate trust, host headers, gateway probes and authentication redirects. Static Web Apps Free custom authentication and linked backend features differ from Standard; the backend must independently protect all API and SSE routes. Confirm external tenant access and explicit authorization.
6. The template proposes SMB mount options for UID/GID 10001; test Azure Files SMB permissions, Git worktree creation/locking, shared paths, persistence, and backup/restore. Network filesystem semantics and costs are not equivalent to local volumes. Test runtime-to-backend and A2A connectivity. The current image may need code/configuration changes for the Azure topology.
7. Run Bicep build/lint and subscription-scoped what-if, then test in an isolated SIT subscription. Verify network/DNS, managed identity RBAC propagation, Key Vault access, image pull, TLS, Postgres LISTEN/NOTIFY, model access, authentication and streaming. The templates are not a substitute for these checks.

The demo assumes one replica, so active work and in-memory replay can be lost at restart. Shared workspace versus private user data must be decided before granting access to external tenants. Do not treat sign-in as tenant isolation. The A$150–250 monthly discussion was an informal planning allowance, not a validated estimate; private networking, gateway, storage, database and model usage must be priced for the actual configuration.

SIT and PRD currently use identical 10.60.0.0/16 address ranges in separate VNets. Change them before peering the environments or connecting to networks with overlapping ranges. The template currently shares one managed identity between backend and runtime; split identities and scope secret access before exposing the demo. Key Vault purge protection makes deleting/reusing a vault name a managed retention operation; plan cleanup accordingly.
